# S15_The_Computing_and_IT_Project - Lesson: The computing and IT project: methodology and practice

## Goal
The learner plans a computing project's requirements, scope and milestones, explains what a computing literature review does and basic research methods appropriate to it, applies risk management and quality assurance to a software project, and structures and critically reflects on a computing project report.

## Syllabus items taught here
- 15a - Project planning for a computing project: requirements gathering, scoping, milestone/Gantt planning
- 15b - Literature review and research methods appropriate to a computing project
- 15c - Software project risk management and quality assurance
- 15d - Writing and presenting a computing project report: structure, evaluation and critical reflection

## How to teach this
Ask the learner to list, unprompted, everything that could go wrong in a solo software project over several months -- before mapping their answers onto formal risk-management categories. Work every algorithm trace, calculation and code example with the learner step by step before revealing the next stage; have the learner predict a program's output before it is run. This is honours-degree material: insist on precise terminology and full justification, not just a right answer. Every computed value, algorithm trace and program output in these files was produced by actually running Python when the course was built, never hand-typed.

#### 15a Project planning for a computing project: requirements gathering, scoping, milestone/Gantt planning
**Project planning.** **Requirements gathering** for an individual computing project typically draws on a review of existing systems/literature, stakeholder input (if any real users are involved) and the project's own aims, producing a clear statement of what the finished system/study must achieve. **Scoping** deliberately bounds the project (what will and will not be attempted) -- essential in a fixed-length project, since an unbounded scope is the single most common reason a project fails to finish; a good scope explicitly states assumptions and exclusions, not just inclusions. **Milestone/Gantt planning** breaks the project into a sequence of concrete, dated deliverables (e.g. literature review complete, design complete, core implementation complete, evaluation complete, draft report complete) with dependencies between them made explicit (e.g. evaluation cannot start before implementation is far enough along to test) -- a Gantt chart visualises this as a timeline of overlapping/sequential bars, making slippage visible early rather than only at the final deadline.

#### 15b Literature review and research methods appropriate to a computing project
**Literature review and research methods.** A computing project's literature review situates the work against existing approaches: what has already been tried for this or a closely related problem, what its strengths/limitations were, and what gap or opportunity the project's own work addresses -- a review that only lists sources without comparing/critiquing them is descriptive, not genuinely a review. **Research methods** appropriate to a computing project vary by project type: an *empirical/evaluative* project (e.g. comparing two algorithms' performance) uses **quantitative methods** (controlled experiments, benchmarking with clearly stated metrics and conditions, statistical analysis of results, as covered in S06); a project involving real users (e.g. evaluating a system's usability) may also use **qualitative methods** (interviews, think-aloud usability sessions, thematic analysis of user feedback); a *design/build* project should still state clear, falsifiable success criteria defined before evaluation begins, not judged informally after the fact.

#### 15c Software project risk management and quality assurance
**Software project risk management and quality assurance.** **Risk management** identifies risks (e.g. a key dependency/library changing incompatibly, underestimating a task's difficulty, scope creep, data unavailability), assesses each by likelihood and impact, and defines a mitigation or contingency plan for the significant ones (e.g. a fallback simpler implementation if the ambitious one proves infeasible in the time available) -- identifying a risk without a corresponding mitigation plan is an incomplete risk analysis. **Quality assurance** in a project context includes the software testing practices from S05 (unit tests, appropriate coverage), but also process practices: regular version control commits with meaningful messages (giving a recoverable history and evidence of the work's genuine progression, important for both practical safety and academic integrity), and a realistic evaluation plan defined before building (to avoid the trap of only evaluating in ways that flatter the finished system).

#### 15d Writing and presenting a computing project report: structure, evaluation and critical reflection
**Writing and presenting a computing project report.** A typical structure: *Introduction* (the problem, its motivation, aims/objectives); *Literature Review* (as above); *Design/Methodology* (what was built or how the study was conducted, and why, with justified choices, not just a description); *Implementation* (key technical decisions and challenges -- not a full code listing/walkthrough); *Evaluation* (results against the success criteria stated at the start, honestly including where the project fell short, not only its successes); *Conclusion and Critical Reflection* (what was learned, what would be done differently with hindsight, and genuine limitations of the work -- a report that claims no limitations at all is generally read as less credible/rigorous, not more, since every real project has some). **Critical reflection** specifically means evaluating one's own work and process with the same rigour applied to any other source, not simply summarising what was done -- honours-level assessment weighs this reflective, evaluative quality highly, distinct from and beyond a mere narrative account of the work.

## Explicitly not here
The technical content evaluated within a specific project (algorithms, statistics, ML, etc.) is covered in the earlier stages; this stage is the project's own methodology and reporting skills.
