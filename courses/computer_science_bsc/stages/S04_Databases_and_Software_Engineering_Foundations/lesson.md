# S04_Databases_and_Software_Engineering_Foundations - Lesson: Databases and software engineering foundations

## Goal
The learner designs an entity-relationship model with correct cardinalities, normalises a relation to 3NF by identifying functional dependencies and anomalies, explains the ACID properties and basic locking, and compares waterfall, iterative and Agile/Scrum lifecycle models with a grasp of requirements engineering.

## Syllabus items taught here
- 4a - Relational database design: ER modelling, primary/foreign keys, 1:1, 1:M and M:N relationships
- 4b - Normalisation: functional dependencies, 1NF, 2NF, 3NF, redundancy and update/insert/delete anomalies
- 4c - Transactions and the ACID properties; basic concurrency control (locking)
- 4d - Software development lifecycle models: waterfall, iterative, Agile/Scrum, requirements engineering

## How to teach this
Show the learner a single denormalised table mixing student and course data with repeated course names, and ask what goes wrong if a course is renamed. Work every algorithm trace, calculation and code example with the learner step by step before revealing the next stage; have the learner predict a program's output before it is run. This is honours-degree material: insist on precise terminology and full justification, not just a right answer. Every computed value, algorithm trace and program output in these files was produced by actually running Python when the course was built, never hand-typed.

#### 4a Relational database design: ER modelling, primary/foreign keys, 1:1, 1:M and M:N relationships
**Entity-relationship (ER) modelling.** An ER model identifies *entities* (things about which data is stored, e.g. Student, Course), their *attributes* (e.g. student_id, name), and *relationships* between entities with a stated *cardinality*: **1:1** (each Student has exactly one StudentCard, and vice versa), **1:M** (one Lecturer teaches many Modules, but each Module has one designated Lecturer), **M:N** (many Students enrol on many Courses -- resolved in the relational model by an associative/junction table, e.g. Enrolment(student_id, course_id), since a relational table cannot directly store a many-to-many link). A **primary key** uniquely identifies each row in a table; a **foreign key** in one table references the primary key of another, enforcing referential integrity (you cannot insert an Enrolment row referencing a course_id that does not exist in Courses).

#### 4b Normalisation: functional dependencies, 1NF, 2NF, 3NF, redundancy and update/insert/delete anomalies
**Normalisation.** A **functional dependency** X -> Y means the value of X determines the value of Y (e.g. student_id -> student_name). **1NF** (First Normal Form): every column holds a single atomic value (no repeating groups or multi-valued fields). **2NF**: 1NF, plus every non-key attribute depends on the *whole* of a composite primary key, not just part of it (eliminates *partial dependency*). **3NF**: 2NF, plus no non-key attribute depends on another non-key attribute (eliminates *transitive dependency*, e.g. student_id -> course_id -> course_name should not sit in the same un-normalised table, since course_name depends on course_id, not directly on student_id). Failing to normalise causes **anomalies**: an *update anomaly* (the same fact, e.g. a course name, stored redundantly in many rows, can go out of sync if only some are updated); an *insertion anomaly* (cannot record a new course until a student enrols on it, if course data only exists attached to enrolment rows); a *deletion anomaly* (deleting the last student enrolled on a course accidentally deletes all record that the course exists).

#### 4c Transactions and the ACID properties; basic concurrency control (locking)
**Transactions and ACID.** A database transaction is a sequence of operations treated as a single logical unit. **Atomicity**: the transaction either completes entirely or has no effect at all (no partial writes survive a failure). **Consistency**: a transaction takes the database from one valid state to another, respecting all constraints (keys, referential integrity). **Isolation**: concurrent transactions do not see each other's uncommitted intermediate state, as if they ran one after another. **Durability**: once committed, a transaction's changes survive even a subsequent system crash. **Concurrency control**: *locking* prevents two transactions from conflicting simultaneous access to the same data -- a *shared (read) lock* allows other readers but blocks writers; an *exclusive (write) lock* blocks all other access until released; holding locks in an inconsistent order across transactions can cause a *deadlock* (each transaction waits forever for a lock the other holds).

#### 4d Software development lifecycle models: waterfall, iterative, Agile/Scrum, requirements engineering
**Software development lifecycle models.** **Waterfall**: strictly sequential phases (requirements, design, implementation, testing, deployment, maintenance), each completed before the next begins -- predictable and easy to manage/document, but poor at accommodating changing requirements discovered late. **Iterative/incremental models**: deliver working software in successive iterations, each adding functionality and incorporating feedback, reducing the risk of building the wrong thing for a long time before anyone sees it. **Agile/Scrum**: development in short, fixed-length *sprints* (commonly 1-4 weeks), each ending with a potentially shippable increment; a *product backlog* (prioritised requirements) is refined into a *sprint backlog*; a daily stand-up, a sprint review and a sprint retrospective structure the team's work and continuous improvement. **Requirements engineering** covers *elicitation* (gathering requirements from stakeholders, e.g. interviews, workshops), distinguishing *functional* requirements (what the system must do) from *non-functional* requirements (performance, security, usability constraints), and *validation* (checking requirements are correct, complete and testable) -- weak requirements engineering is a leading cause of project failure regardless of which lifecycle model is used.
