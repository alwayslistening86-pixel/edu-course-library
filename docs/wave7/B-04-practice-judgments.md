Then I read the scripts they call: `error_log.py`, `item_mastery.py`, `diagnostic_gate.py`, `confidence_update.py`, `review_math.py`, `cards` (`tutorlib/cards.py`), `deck_add.py`, `record_stage_result.py`, `record_grading.py`, `record_mock.py`, `remediation_state.py`, `calibration.py`, `practice_pick.py`, `session_state.py`, `goal_map.py`, plus `tutorlib/consent.py`, `tutorlib/state.py` and `tutorlib/schemas/subjects.json` (what `state.save` actually validates). Skill line numbers are the file's own line numbers (`cat -n`). "Script check" quotes real code; where I found no check I say "none". Not read in depth: `next_items.py`, `plan_estimate.py`, `profile_set.py`, `apply_capabilities.py`, `roster_apply.py` (they read state or take learner-stated settings, not teaching-model judgments).

Common to every script row below: `state.save` runs `schema.validate`, which only checks types and enums (e.g. `error_patterns[].cause` enum, `syllabus_status` enum `pass|fail|unsat|withheld`, `stage_id` "string"); it does not check that a `stage_id` or `item_id` exists in the course. Consent (`tutorlib/consent.py`): `SIGNAL` (error_patterns, confidence, item_mastery, history rows, summaries) persists under `granted` only; `PROGRESS` and `SCHEDULING` also under `limited`.

## Reasons (class, keyed by row)

1. examiner-only: it is a reading of what a learner said; no item key decides it (low stakes, it only opens or skips a question).
2. examiner-only: needs the learner's reasoning compared to their answer (free text).
3. script-markable: for MC, numeric and cloze items a pure function of (item key, learner answer) decides right/wrong, as ADR 0010 says ("Cheap deterministic marking already exists in principle").
4. examiner-only: free-text or worked answers need rubric-level judgment.
5. examiner-only: causal diagnosis from elicited reasoning, named in the ADR as the call a local voice must not make; the enum limits the output but not the choice.
6. checkable: the model proposes an id and a script can verify it exists in that stage's `misconceptions.json` (today it does not).
7. checkable: the item/stage come from the item the script served (`next_items.py`, `practice_pick.py`), so a script can verify the tag matches.
8. examiner-only: free text that describes a belief; unverifiable, though it only feeds humans and the auditor.
9. script-markable: it follows from `current_phase`, which a script already owns.
10. checkable: correctness is script-markable for deterministic items; "confident" is a model claim; a script can verify there is an unresolved entry and a correct answer in the item key.
11. script-markable: a pure function of (item key, answer) for deterministic items; no skill uses it, so this is a capability, not a current flow.
12. script-markable: `next` already knows what it recommended; the model only reports it back.
13. script-markable: `answers_for` returns the cloze key, so right/wrong is string comparison.
14. examiner-only: "carries the key reason" is a free-text meaning judgment (basic and worked_step cards could be partly checkable if the back is short and exact, but the skill does not say so).
15. examiner-only: whether a card is true and well-posed is content judgment; the script checks form only.
16. checkable: the tags can be verified against `curriculum_map.json` and `rubric.json` (the data exists; no check is wired).
17. script-markable: the candidate set comes from `mature`; the yes comes from the learner.
18. examiner-only: grading against a rubric, the core examiner task in ADR 0010 (marks, M/A/B method marks).
19. checkable: the verdict is derivable from row 18's marks and the rubric's `pass_threshold` (which `record_grading.py` already hashes), so a script could verify it.
20. script-markable: event follows from the stage verdict and the remediation entry; `--misconception` follows from `error_patterns`.
21. checkable: the cause should equal one of the stage's logged `error_patterns`.
22. script-markable: determined by a recorded pass.
23. checkable: "done when" in `tutor-core` can be tested against `item_mastery`/`practice_used`; today it is purely the model's call.
24. examiner-only: grading the exam against `exam_rubric`.
25. script-markable: the rating is the learner's own; the result is a copy of row 19.
26. examiner-only: free-text summary, not verifiable; no progress effect.
27. examiner-only: same as 18 (marks against a mark scheme); only the arithmetic is script-checked.
28. examiner-only: same as 5.
29. checkable: the model proposes, `set_goal` verifies ids against the course (already does); the learner confirms.
30. script-markable: learner-supplied date, validated.
31. examiner-only: requires reading and comparing live web pages.
32. examiner-only: judgment over specification and learner patterns.

## Observations

**Writes with no script-side check on the model's input**
- `error_log.py append`: `stage_id`, `item_id`, `misconception_id`, `rubric_criterion` and `note` are accepted as written. Only `cause` and `source_phase` are validated. An `item_id` typo creates a phantom `item_mastery` entry (rows 5-8).
- `remediation_state.py record`: `cause` is any string (row 21).
- `record_stage_result.py apply`: only `stage_id in stage_ladder` and `pass|fail`; no link to `record_grading.py` marks, `pass_threshold`, `current_phase == test` or convergence (row 19). `session_state.py phase test` and `roster` likewise trust the model (row 23).
- `confidence_update.py apply` takes the event on trust and is not cross-checked with `record_stage_result.py` (row 20).
- `record_mock.py`: question ids and total marks are not checked against the bank or the assembled paper (row 27).
- `diagnostic_gate.py` and `review_math.py` use `_bool`/`== "true"`: a typo such as `yes` or `True ` is read as false, so a correct recall is recorded as a lapse (rows 1, 2, 13).
- Course-file writes by the model (`change.md`, `grounding_status`, `last_live_recheck`, `misconceptions.json` additions) have no script at all; only `scan_untrusted.py` runs afterwards (rows 31-32).

**What matters most if the teaching voice were a weaker model**
1. Rows 5 + 7 (the diagnosis): one `error_log.py append` writes the cause, an `item_mastery` BKT drop, the diagnostic-gate counters, the auditor's cohort rollup and stage-recap's extra cards. A wrong `cause` or `item_id` propagates to all of them and no script can notice.
2. Rows 18-20 (grade, pass/fail, confidence): `pass` advances `current_stage` and feeds the level ledger, the highest-consequence write, and nothing ties it to the per-criterion marks.
3. Rows 3, 10, 13 (right/wrong marks): these are already near-deterministic for MC, numeric and cloze items, but today the model supplies the verdict, so they are the cheapest rows to take away from the voice (script-markable).
4. Row 23 (phase and `test_pending_convergence`): a mistaken "ready" moves a course into the testing round with no mastery evidence.

**Skill prose and script disagree, or are unclear**
- course-runner/SKILL.md:23 says to run `diagnostic_gate.py` then `error_log.py append` "after each wrong answer in practice or test", but lines 134-155 say the gate is deliberately narrow ("If `fire` is `false`, keep teaching normally"). Trigger a (two unresolved misses on the item) and trigger b (3+ unresolved entries of one cause) count only entries already in the log, so if only fired moments are logged those triggers can never accumulate. Which reading is intended is unclear. The log, and therefore `item_mastery`, depends on it.
- `item_mastery` only ever receives wrong answers (via `append`) and corrections (via `resolve`). No skill tells the model to record a plain correct practice answer (the `observe` direct call is only in the script docstring), so mastery is biased low and untouched by clean successes. The brief's example "marking a practice answer right/wrong -> item_mastery.py" is not a documented flow.
- exam-simulator/SKILL.md:9 says a mock "never changes ... " progress state, but its `error_log.py append ... test` calls (line 138) move `item_mastery` and count toward `diagnostic_gate.py` triggers for the stage.
- diagnostic_gate.py docstring says trigger a is "two consecutive misses"; the code counts two unresolved misses on the item in the stage, not consecutive ones.
- review-scheduler/SKILL.md:49 says a brand-new card needs no script call, while `deck_add.py` computes `due_at_slot` itself and stage-recap/SKILL.md:22 still says to set "`due_at_slot` starting at the next slot" in the card (the script ignores any such field).
- course-runner/SKILL.md:9 lists `last_live_recheck`, `grounding_status` and `change.md` as "owned" but the procedure (lines 64-67) has the model write them by hand; no script owns them, unlike the "never hand-write a script-owned field" rule.
