Scope: every kind of personal data the generic-tutor plugin holds about a learner. Read-only research; nothing was run.
Paths are relative to `plugin/generic-tutor/` unless stated. `<L>` = `profile/<user_id>/` (the learner folder).

## 2. Where personal data could leak outside the learner folder

1. **Backups**: default `<profile_root>/../backups/` (`backup_profile.py:65-66`), so next to `profile/`. Full copies, including data written under limited consent and `.pre-migrate*.bak` files (`backup_profile.py:32`). `/erase` and `purge_history` do not remove them (`PRIVACY.md`, `erase_profile.py:52`). The zip file name includes the `user_id`.
2. **Sync folders**: `INSTALL.md:20` and `:42` tell the user to keep backups outside synced folders but say synced backups are acceptable "if you accept that they contain personal data". Nothing in code prevents `--out` pointing at a synced folder.
3. **Safety backup on restore**: `restore_profile.py:27` creates a second `-pre-restore.zip` of the learner being replaced, in the backups folder, with no expiry found.
4. **Exports**: written to any learner-chosen path outside the profile root (`export_profile.py:57-59`). Include SQLite history and the ledger. Not removed by `/erase`.
5. **Dashboard and printable summary**: written to any path outside the learner folder (`dashboard_html.py:156-165`), containing `learner_id` and, for the summary, the recipient name. Not removed by `/erase` (`dashboard_html.py:19-20`). Intended to be handed to a third party; the page notes it is personal data (`:123-124`).
6. **Hook state in system temp**: `generic-tutor-hooks/<session>.json` holds the learner id and the command (`hook_guard.py:40-60,207-214`). Outside the learner folder, no cleanup.
7. **Temporary copies**: backup writes a temp SQLite copy to the system temp dir (`backup_profile.py:41`); `drop_preview` copies the whole `profile/` tree to the temp dir (`roster_apply.py:109-111`). Both are removed on normal exit.
8. **Error output**: scripts print `{"error": "<ExcType>: <message>"}` to stdout (`cli.py` `emit`/`EXPECTED_ERRORS`); messages can include file paths (which contain the `user_id` and course id) and, for `state.StateError`, file locations. No script writes a log file; `grep` for `logging` found none. `error_log` returns the full entry with `note` on stdout (`error_log.py:150-160`), which lands in the Claude conversation.
9. **Model host**: everything the learner types and every profile field read into context is processed by Claude (`PRIVACY.md` Third parties). No telemetry from the plugin (`PRIVACY.md`).
10. **Connectors**: `uk-legal`, `govuk` (opt-in) see only queries sent to them (`PRIVACY.md`). Not inspected further here.
11. **CI logs**: `.github/workflows/plugin-tests.yml` runs `unittest`, lint and `tools/scan_repo.py`; no step reads a real `profile/` (the folder is git-ignored, `.gitignore`). `validate-courses.yml` is for the private content repo. I found no CI step that handles learner data; tests use fixtures. I did not open `tools/scan_repo.py`.
12. **Eval runs**: `claude -p` is invoked with a system prompt from plugin text and synthetic prompts, `cwd` an empty temp dir, no session persistence (`evals/backends.py:24-29`). Error text from the subprocess (first 300 chars) is kept in reports (`:36`). Prompts are synthetic, so no learner data was found going there.

## 4. What the system does NOT hold (checked)

- **Answer text**: SQLite grading table is "indexes and numbers only, never answer text" (`DATA_MODEL.md`); the ledger holds ids and numbers (`ledger.py:24`). The JSON `error_patterns[].note` is the exception: it describes the mistake in free text.
- **Chat transcripts**: no script stores conversations. Evals run with `--no-session-persistence`.
- **School, class or teacher names, address, date of birth, age, email, phone, photo**: no such field in `schemas/student_profile.json`, `subjects.json`, the SQLite DDL, or `profile_set.py`'s `TEXTS`. `identity` is declared as a bare `"type": "object"` (`schemas/student_profile.json:10`), so the schema does not forbid extra keys; the scripts only set the four named ones. The user's email in the session context is not read by any script.
- **Calendar dates beyond**: activity timestamps exist (ledger `ts`, SQLite `created_at`, `last_updated`, `set_on`, mock `date`); `DATA_MODEL.md` says availability is "rate only, never dates" and `target.date` is "the only calendar date stored", which is not accurate given those timestamps.
- **Guardian or parent data**: none; accounts and automatic parent reports are out of scope (`PRIVACY.md` Minors). Only the recipient label on a summary.
- **Device, IP or telemetry data**: none (`PRIVACY.md` "No telemetry").
- **Other learners' data inside a learner's files**: isolation by code (`paths.learner_dir`, symlink refusal) per export and erase docstrings.

## 5. Gaps (no retention rule, or not covered by erase / purge)

1. **Backups have no retention rule**: no expiry, rotation or list/delete command found; `/erase` leaves every earlier backup and every `-pre-restore.zip` (`PRIVACY.md`, `erase_profile.py:52`). Backups also include data written under limited consent, and a backup taken before `revoked` keeps SIGNAL data.
2. **Exports and dashboard/summary HTML have no retention rule** and are outside erase, by design; the code gives no list of where they were written, so the learner cannot be shown them.
3. **Hook state files** in the system temp dir hold the learner id and are not removed by `/erase` or anything else (`hook_guard.py:41,54-60`).
4. **`purge_history course` skips `.pre-migrate*.bak` files** for that course: it removes only `<course>.json` and `<course>_review_deck.json` (`purge_history.py:67-71`), so a migration copy with the full old progress file remains. `.bak` files are also copied into backups.
5. **`purge_history history` does not clear the JSON copies of signals** (`error_patterns`, `item_mastery`, `confidence`, `mock_results`, `last_session_summary`, `calibration`); it removes only the SQLite files and ledger (`purge_history.py:8-10,29,80-83`). Documented as "current progress untouched", but those fields are SIGNAL data with no separate removal command.
6. **No erasure of free-text fields alone**: no command clears `error_patterns[].note`, `last_session_summary` or `learning_signals.notes` while keeping progress. Only whole-course purge or `/erase`.
